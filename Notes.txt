## API Testing ##

--> look for documentation of APIs in the website:
	-> /api
	-> /swagger/index.html
	-> /openapi.json


--> Use Burp crawler to crawl the site for APIs and audit OpenApi documentations 
    or any other documentation in JSON or YAML format.
--> Parse the documentation using OpenAPI Parse App.
--> Tools - Postman, SoapUI
--> Also some APIs might not be triggered by the crawlers through browsing,
    so look for JS files for other references to the hidden APIs.


-->Then after that find the HTTP Methods the API supports.
	->To do this use the burp HTTP verb list in intruder to automatically cycle through
	 a range of methods.
-->then identify supported content types: modify the content-type header.
	Types of bugs:
	->By pass flawed defences.
	->differences in processing logic.
	->trigger errors to disclose additional information.

  ** Always put the " Content-Type " Header after the header " Accept: */*  "

-->Sometimes there are hidden parameters to the APIs, which can alter the behaviour of
the application in various ways, to find these you can use: 
"" Param miner BApp ""
 which can guess upto 65,535 params names per requests, it automatically guesses names that are relevant 
to the application based on the info taken from scope.


-->Mass assignment vulnerabilities 
	1)this is also called auto binding, this can advertently create hidden parameters
	which were never intended to be processed by the developer.

	2)This happens when - software frameworks automatically bind request parameters
	to fields on an internal object, so again attacker controlled input directly processed.
